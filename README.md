# keti-reconfig

KETI TSN 재구성 데모. 안드로이드 태블릿이 **LAN9662 스위치**와 **패스 모듈**을 직접 제어하고,
스위치 상태·성능을 태블릿에 표시한다.

이전 데모(`hwkim3330/pleos`)와의 차이는 **중간 감독자(7인치 ESP)를 없앴다**는 것이다.
그 보드가 멈추면 체인 전체가 죽었고, 실제로 그렇게 죽었다. 태블릿이 각 장치에 직접 붙는다.

## 구성

```
                    ┌── ? ──> 스위치 컨트롤러 ESP32-S3 ──[Ethernet]──> LAN9662/9692
Android 태블릿 ─────┤          (W5500, 192.168.1.20)                  (192.168.1.10)
                    │
                    ├── BLE ─> 패스 모듈 1 (SuperMini)  ┐ 페일 인젝션
                    └── BLE ─> 패스 모듈 2 (SuperMini)  ┘ 모듈에 장착
```

**패스는 2개다.** 이전 데모의 Path 3은 7인치 ESP 자체의 GPIO였으므로, 7인치를 걷어내면서
같이 사라졌다. 노드 2개 = 경로 2개.

## LAN9692 로 옮겼다 (2026-08-07)

벤치는 이제 **LAN9692VAO - EV09P11A0 (UNG8420)**, VelocitySP-2025.03-1 이다.
`/dev/ttyACM1` (MCP2200; 9662 는 MCP2221 이었다), 관리 IP `192.168.1.12`,
카탈로그 `440057a11e66eed82bc8e838347f694c`, **포트 12개 + L3V1**.
ESP 는 **포트 12** 에 물려 있다.

이행에 필요했던 것은 **SID 테이블 재생성과 상수 두 개**(스위치 IP, 업링크 포트)뿐이었다.
앱은 한 줄도 고치지 않았다 — 이름도 포트 목록도 장비에서 읽기 때문이다. 인터페이스 응답이
1390 B / 6블록에서 **6546 B / 26블록**으로 커졌지만 블록 조립이 그대로 처리했고,
포트는 런타임 발견이라 13개가 저절로 잡혔다. 아래 규칙들이 값을 한 지점이다.

SID 값 자체는 IETF 표준 모듈이라 두 장비에서 같았다. **그래도 가드는 체크섬 기준이어야
한다** — 같았다는 것은 사후에 안 사실이고, 미리 알 수 있는 것이 아니다.

```
KETI_CATALOG=<checksum> node tools/gen_sid_table/generate.mjs
```
캐시에 카탈로그가 둘 이상이면 어느 것을 쓸지 **명시해야** 한다. 추론하지 않는다.

### 원래 계획 (LAN9662 시절 기준)

지금 벤치에 있는 것은 **LAN9662**지만, 최종 대상은 **LAN9692**다. 프로토콜 스택은 같으므로
(MUP1 / CoAP / CBOR / CORECONF, VelocityDRIVE-SP) 9662로 개발하는 것은 유효하지만,
**9662에서만 참인 것을 코드에 굳히면 9692에서 조용히 깨진다.** 지켜야 할 것:

- **포트 수를 박지 말 것.** 9662는 데이터 포트가 2개다. 9692는 훨씬 많다. 포트 목록은
  항상 `/ietf-interfaces:interfaces`를 읽어서 **런타임에 발견**한다. 대시보드 레이아웃도
  포트 수에 따라 늘어나야 한다.
- **SID를 상수로 박지 말 것.** SID는 YANG 카탈로그에 종속이고, 카탈로그는 장비마다 다르다
  (모듈 집합과 리비전이 다르다). 미리 뽑은 SID 테이블에는 반드시 **그 테이블을 만든 카탈로그
  체크섬을 함께 심고**, 장비가 보고한 체크섬과 다르면 **거부하고 알린다**. 조용히 잘못된
  노드를 건드리는 것이 최악이다. `keti-tsn-cli`가 캐시를 체크섬으로 키잉하는 것과 같은 이유다.
- **IP 경로가 9692에서는 일급이다.** `keti-tsn-cli`의 Ethernet 모드(UDP/CoAP 5683)와
  `setup/setup-ip-static.yaml`은 원래 9692를 겨냥해 쓰여 있다.
- 아래 "확인된 사실"의 수치는 전부 **9662 기준**이다. 9692로 옮기면 다시 측정한다.

## 확인된 사실 (2026-08-07 실측, LAN9662 기준)

측정하지 않은 것은 아래 "미확인"에 따로 적는다.

### LAN9662 스위치

| 항목 | 값 |
|------|-----|
| 접속 | `/dev/ttyACM2` — Microchip MCP2221 USB-UART 브리지 (`04d8:00dd`) |
| 프로토콜 | MUP1 (시리얼), CoAP/CBOR over UDP 5683 (IP) |
| YANG 카탈로그 체크섬 | `5151bae07677b1501f9cf52637f2a38f` — 54개 YANG / 54개 SID |
| 데이터 포트 | `1` (oper-status up), `2` (down) — 둘 다 ethernetCsmacd |
| 관리 IP (9662) | `L3V1` = **192.168.1.10/24** static, oper-status up, MAC `52-D0-9D-B2-96-00` |
| fetch 왕복 | 전체 인터페이스 트리 약 0.4 s → **1 Hz 폴링 여유** |

관리 IP는 원래 없었다. `keti-tsn-cli`의 `setup/setup-ip-static.yaml`로 L3 VLAN 인터페이스를
만들어 부여했고, `save-config`로 플래시에 저장했다. 최초 설정은 MUP1(시리얼)로만 가능하다.

읽히는 데이터: 포트별 in/out octets·unicast·multicast·broadcast·discards·errors,
이더넷 프레임 통계(FCS/oversize/undersize 오류 포함), 브리지 포트 통계,
그리고 **TAS 게이트 파라미터**(`ieee802-dot1q-sched-bridge:gate-parameter-table`).
대시보드 그래프에 필요한 것은 이미 다 나온다.

### ESP32-S3 보드 2개

보드는 3개다. MAC 으로 구분한다 (포트 번호는 꽂는 순서에 따라 바뀐다).

| MAC | 칩 | 플래시 / PSRAM | 역할 |
|------|-----|---------------|------|
| `28:84:85:6F:46:E8` | ESP32-S3 | 4MB 내장(XMC) / 2MB | **패스 모듈 1** (SuperMini) |
| `28:84:85:6F:48:E0` | ESP32-S3 | 4MB 내장(XMC) / 2MB | **패스 모듈 2** (SuperMini) |
| `28:84:85:80:9B:D0` | ESP32-S3 | 16MB / 8MB | **스위치 컨트롤러** (W5500 탑재) |

### 스위치 컨트롤러의 W5500

| 신호 | 핀 |
|------|-----|
| SCK  | GPIO48 |
| MOSI | GPIO21 |
| MISO | GPIO47 |
| CS   | GPIO45 |
| RST  | GPIO 에 안 물렸거나 풀업 — 건드리지 않아도 응답한다 |

**이 핀맵은 데이터시트가 아니라 전수 탐색으로 찾았다.** 공개된 핀맵(Waveshare ESP32-S3-ETH
포함) 7종을 시도했지만 전부 무응답이었다. 찾은 방법은 `tools/eth_probe/`에 있다 — SPI 를
비트뱅잉하고 매 클럭마다 GPIO 입력 레지스터를 통째로 스냅샷하면 모든 핀이 동시에 MISO 후보가
되므로, (SCK, MOSI, CS) 삼중조 24,360 개를 **5초**에 훑는다. 확인은 `tools/eth_verify/`가
리셋값이 알려진 레지스터 3개로 한다: VERSIONR `0x04`, RTR `0x07D0`, RCR `0x08` — 전부 일치.

앞선 시도들이 왜 실패했는지도 기록해 둔다. **옥탈 PSRAM(8MB)을 쓰면 GPIO33~37이 PSRAM
버스에 묶인다.** 그 핀들을 SPI 후보로 넣은 시도는 애초에 성립할 수 없었다.

### 이더넷 경로 (실측)

- W5500 PHYCFGR `0xBF` → **link UP, 100M, full duplex**. 케이블이 이미 물려 있다.
- ESP static `192.168.1.20/24` → 스위치 `192.168.1.10:5683` 으로 CoAP GET 전송,
  **스위치가 응답**했다 (`4.02 Bad Option` — `/.well-known/core` 를 지원하지 않을 뿐,
  도달성과 CoAP 응답성은 증명됨. VelocityDRIVE-SP 는 CORECONF 의 SID 경로를 쓴다).

즉 **이더넷 전송은 실재하고**, 그 위의 CORECONF/CBOR/delta-SID 는 순전히 소프트웨어 문제다.

### 설정 쓰기 (iPATCH)

읽기와 같은 CoAP 엔드포인트에 **code 0.07 (iPATCH), Content-Format 142, Accept 140**.
페이로드 형태는 **장비가 정해줬다**:

```
A1 82 19 07F4 61 32 F5   =  {[2036 "enabled", "2"]: true}
```

인스턴스 식별자가 **리프 SID**를 지목하고 값이 바로 온다. 처음엔 리스트 엔트리를 지목하고
리프를 그 안에 중첩했는데(`{[2033,"2"]: {3: false}}`), 스위치가
**`List keys not allowed`, error-data-node 2033** 으로 거부했다.

**중요한 진단 교훈**: 그 잘못된 요청을 이더넷으로 보내면 **아무 응답도 오지 않는다.**
같은 요청을 시리얼로 CLI 를 통해 보내야 위 오류 메시지가 보였다. 이더넷 쪽이 조용하다고
해서 요청이 도달하지 않은 것이 아니다 — **CLI 로 시리얼에서 재현해 보는 것이 가장 빠른
진단 경로다.**

태블릿 → BLE → ESP → 이더넷 iPATCH 로 포트를 켜는 것까지 실기 확인:
`type 2 (ACK), code 2.04 Changed`, CLI 로 되읽어 `enabled: true`.

**포트 1은 컨트롤러 자신의 업링크라 끌 수 없다.** 끄면 되돌릴 경로가 사라지고 시리얼로만
복구된다. 펌웨어가 거부하고(`!ACK:PORT:REFUSED`), 앱도 그 버튼을 `uplink` 로 비활성 표시한다.
버튼을 숨기지 않고 비활성으로 두는 이유는, 없는 버튼은 어디 갔나 찾게 만들기 때문이다.

**탐지하지 않고 상수로 적어둔다** (`kProtectedPort`). 컨트롤러는 자기 프레임이 어느 포트로
들어오는지 브리지 FDB 를 뒤지지 않고는 알 수 없고, **짐작하는 가드는 적어둔 가드보다 나쁘다.**
다른 리그에 옮기면 이 값을 바꿀 것.

### 이더넷 CoAP 는 키 붙은 인스턴스 조회를 받지 않는다

`[[SID, "포트"]]` 형태의 iFETCH 는 이 장비의 **이더넷 CoAP 엔드포인트에서 4.00 으로 거부된다.**
같은 바이트를 CLI 가 MUP1(시리얼)로 보내면 **성공한다.** 확인한 범위:

- 요청 바이트가 CLI 와 **완전히 동일**함을 확인했다 (`81 82 19 5A3D 61 31`, cbor-x 출력과 대조)
- SID 를 바꿔도(gate-parameter-table 23101, interface 2033) 같은 결과
- Block2 옵션을 빼도 같은 결과
- 오류 본문을 카탈로그로 해독: `error-tag: operation-failed`,
  `error-app-tag: malformed-message`, `error-data-node: 0`

키 없는 서브트리 조회(`[SID]`)는 같은 경로에서 정상 동작한다. **그래서 포트별 상세는 따로
요청하지 않는다** — 게이트 파라미터는 이미 인터페이스 서브트리 안에 실려 오므로 그것을
파싱한다. 추가 요청 0회로 끝나므로, 우회가 아니라 더 나은 설계가 됐다.

**진단 순서**: 이더넷에서 실패하면 CLI 로 시리얼에서 같은 요청을 재현할 것. 이더넷은 침묵
하거나 4.00 만 주지만, 시리얼 쪽 CLI 는 오류 본문을 사람이 읽게 찍어준다.

### 주소 계획

| 장치 | 주소 |
|------|------|
| LAN9662/9692 스위치 | `192.168.1.10` |
| 스위치 컨트롤러 ESP | `192.168.1.20` |
| 태블릿 | `192.168.1.30` (예정) |

DHCP 서버가 없는 폐쇄망이므로 전부 static.

**SuperMini 상태 LED: GPIO48 의 어드레서블 RGB (WS2812).** 이 보드에 제어 가능한 LED 는
그것 하나뿐이다(전원 LED 는 별도이고 제어 불가).

처음엔 GPIO21 로 잘못 적었다. 그때 프로브는 후보 4개를 **번호가 붙은 단계**로 순서대로
점등하고 "몇 번이 켜졌나"를 물었는데, 주기의 시작을 못 보면 몇 번째인지 알 수 없어서
답이 애매해졌다. 지금 `tools/led_probe/` 는 후보마다 **다른 색을 4초씩** 잡고 있는다 —
빨강이면 21, 초록이면 48, 파랑이면 38. 색이 곧 답이라 한 번 보면 끝나고, 실제로 초록만
나왔다. **육안 확인이 필요한 프로브는 "몇 번째"가 아니라 "무엇"을 묻게 만들 것.**

## 패스 모듈 (firmware/path_module)

두 보드에 같은 펌웨어를 굽는다. **자기 번호는 MAC 으로 정한다** — 빌드 플래그가 아니라
칩에서 나오므로 엉뚱한 파일을 구워 두 모듈이 뒤바뀔 수 없고, 등록되지 않은 보드는
`KETI-PATH-UNKNOWN` 으로 광고해 스스로 이상함을 드러낸다.

| 항목 | 값 |
|------|-----|
| 인젝션 릴레이 | **GPIO13** — HIGH = 고장 주입, LOW = 정상 |
| 상태 LED | GPIO48 WS2812 — **색**은 정체+고장(패스1 초록 / 패스2 파랑 / 고장 빨강), **속도**는 태블릿 링크(연결=2초 주기, 없음=0.5초 주기). 균등 깜빡임 |
| BLE 이름 | `KETI-PATH1` / `KETI-PATH2` |
| 서비스 UUID | `9a1e0001-4d3b-4a2f-9c6e-3f1d7b8a2c40` |
| 제어 특성 | `9a1e0002-…` (read / write / notify) |

명령(태블릿 → 모듈): `!SET:FAULT`, `!SET:NORMAL`, `!SYNC`
상태(모듈 → 태블릿): `!STATE:<seq>:<path>:<NORMAL|FAULT>:<relay>:<event>`, 1 Hz 하트비트 포함

릴레이 레벨은 핀을 출력으로 바꾸기 **전에** 먼저 LOW 로 써 둔다. 그렇게 하지 않으면 리셋
과정에서 릴레이가 순간적으로 닫힐 수 있다.

LED 표시 방식은 두 번 갈아엎었다. **밝기 페이드는 안 보인다** — 체감 밝기가 로그에 가까워
40→100% 램프가 66→100%처럼 읽히고, 작고 밝은 LED 에서는 그냥 켜져 있는 것으로 보인다.
**거의 켜두고 짧게 윙크하는 방식도 별로다** — 리듬이 아니라 결함처럼 보인다. 균등한
깜빡임이 답이다.

깜빡이는 이유는 전력이 아니다. 이 LED 는 한 자리 mA 인데 BLE 켠 보드는 40~100 mA 다.
**켜져만 있는 LED 는 얼어붙은 보드와 구별되지 않기 때문**이고, 리듬만이 펌웨어가 아직
돌고 있다고 말해준다.

**태블릿이 끊기면 정상으로 되돌린다.** 어떤 고장을 시연 중이었든, 링크를 잃은 상태에서
안전한 쪽은 트래픽이 흐르는 쪽이다.

`seq` 는 장식이 아니다. GATT 연결만 보는 콘솔은 조용해진 링크와 죽은 링크를 구별하지
못하고 낡은 값을 현재값처럼 보여준다 — 이전 데모에서 실제로 그렇게 당했다.

## 스위치 컨트롤러 (firmware/switch_controller)

ESP32-S3 + W5500 이 이더넷으로 스위치의 CORECONF 를 직접 말한다. **실기 검증됨.**

요청 형태는 `keti-tsn-cli` 의 `buildiFetchRequest` 에서 그대로 가져왔다:
**FETCH (0.05), Uri-Path `c`, Content-Format 141, 페이로드는 SID 배열의 CBOR.**

카탈로그 체크섬 조회(SID 29304) 실측 결과:

```
-> FETCH /c  payload: 81 19 72 78            (CBOR [29304])
<- 2.05 Content, 22 bytes
   BF 19 72 78 50 5151BAE07677B1501F9CF52637F2A38F FF
   = {29304: h'5151...'}  -> SID 테이블과 일치
```

응답을 읽을 때 두 가지를 처음에 틀렸고, 둘 다 위 덤프에 그대로 보인다:
맵이 **무한길이**(`BF` … `FF`)이지 개수가 붙은 맵이 아니고, 체크섬은 텍스트가 아니라
**바이트열**이라 16진수로 렌더링해야 한다. 짐작한 형식이 아니라 실제 바이트가 기준이다.

### SID 테이블 생성기 (tools/gen_sid_table)

`paths.yaml` 에 필요한 YANG 경로를 적고 `node generate.mjs` 를 돌리면
`firmware/switch_controller/sid_table.h` 가 나온다. 카탈로그는 `keti-tsn-cli` 의 캐시에서
읽고, **캐시 디렉터리 이름이 곧 체크섬**이라 그것이 헤더에 함께 박힌다.

- 하나라도 해석에 실패하면 **부분 테이블을 내보내지 않고 실패한다.** 부분 테이블은 펌웨어에
  조용한 구멍을 만든다 — 되는 경로만 묻고 안 되는 경로는 언급조차 하지 않게 된다.
- 경로는 선행 슬래시가 있어도 없어도 받는다(카탈로그 키에는 슬래시가 없다).

현재 6개 항목: `ietf-interfaces:interfaces` (2005), `ietf-system:system-state/platform`
(19024), interface/name/oper-status/statistics.

## 태블릿 콘솔 (apps/keti_reconfig_console)

태블릿이 **유일한 BLE 센트럴**로 세 페리페럴에 동시에 붙는다: `KETI-SWITCH`, `KETI-PATH1`,
`KETI-PATH2`. 이전 데모에서 ESP32 를 센트럴로 쓴 것이 멈춤의 원인이었고, 이 구조에서는
어떤 ESP 도 그 코드 경로를 타지 않는다.

**실기 검증 완료 (2026-08-07):**

- 세 링크 동시 연결 — 헤더에 `Switch: live · Path 1: live · Path 2: live`
- 스위치: Ethernet up, **3 ports**, 스냅샷 번호 증가, 포트별 실시간 처리율
  (포트 1 = 8.2 kbps, L3V1 = 8.1 kbps, 포트 2 = DOWN 0.0 kbps)
- `Inject fault` → 모듈 시리얼이 `relay=GPIO13 NORMAL` → **`FAULT`**,
  `Recover` → **`NORMAL`** 복귀. 앱 표시(`relay closed` / `relay open`)와 일치.

마지막 항목이 중요하다: 확인을 **앱의 자기 주장이 아니라 모듈 자신의 시리얼**로 했다.
앱이 자기가 보낸 명령을 근거로 상태를 그리면 아무것도 증명하지 못한다.

### 연결됨과 신선함은 다르다

헤더의 칩은 `live` / `silent` / `offline` 세 가지다. GATT 링크는 상대가 말을 멈춰도 살아
있으므로, 링크만 보는 콘솔은 낡은 값을 현재값으로 보여준다 — 이전 데모에서 실제로 그렇게
당했다. 그래서 모든 스냅샷에 `seq` 가 실리고, 6초 이상 조용하면 `silent` 로 바뀌며 수치에
"지금이 아니다"라고 명시한다.

처리율은 연속한 두 스냅샷의 차분으로 계산한다. 카운터는 스위치가 재부팅하면 되감기므로
음수 차분은 처리율로 쓰지 않는다.

## 스위치 여러 대 (스위치당 컨트롤러 하나)

RECON 은 ZCU 3대가 각자 LAN9692 를 갖는 구조다. 그래서 **컨트롤러도 스위치당 하나**가 되고,
코드는 그 전제로 만들어져 있다.

**보드를 하나씩 붙이면 된다. 한꺼번에 셋을 붙일 필요가 없다** — 오히려 하나씩 붙이는 편이
각 보드를 독립적으로 확인할 수 있어 낫다.

새 컨트롤러를 추가하는 것은 `switch_controller.ino` 의 `kControllers` 에 한 줄이다:

```cpp
static const ControllerConfig kControllers[] = {
    {0x288485809BD0ULL, 1, 20, 12, "12"},   // mac, 스위치번호, 자기 IP 끝자리, 스위치 IP 끝자리, 업링크 포트
    // {0x............ULL, 2, 21, 22, "12"},
};
```

**펌웨어는 하나다.** 보드는 자기 MAC 으로 표를 찾아 번호·자기 주소·스위치 주소·업링크 포트를
정한다. 표에 없는 보드는 **주소를 아예 안 가진다** — 스위치 1 의 것을 빌려 쓰면 같은 스위치를
두 컨트롤러가 대변하게 되고, 그건 대놓고 동작 안 하는 것보다 나쁘다.

보드 하나당 알아야 할 것은 셋뿐: 보드 MAC, 그 스위치의 관리 IP, ESP 가 꽂힌 포트 번호.

- 컨트롤러는 **MAC 으로 자기 번호를 정해** `KETI-SWITCH1/2/3` 으로 광고한다. 패스 모듈과
  같은 방식이고, 잘못 구워 스위치 1 이 두 대 생기는 일을 막는다. 미등록 보드는
  `KETI-SWITCH-UNKNOWN`.
- 콘솔은 스위치별로 스냅샷·TAS·GCL 을 따로 보관한다. **어느 스위치의 줄인지는 그 줄이 도착한
  연결에서 안다** — 줄 안에 번호를 또 넣지 않는다. 같은 사실의 출처가 둘이면 언젠가 어긋난다.
- **스위치가 하나면 선택 UI 가 나타나지 않는다.** 헤더 칩도 그냥 `Switch` 다. 한 대짜리
  리그에 의미 없는 단계를 강요하지 않고, 두 대째가 붙는 순간 선택줄이 생긴다.
- 광고 이름은 열거된 셋만 받는다. 패턴으로 아무 "스위치"에나 붙으면 옆 벤치에 연결된다.

## 게이트 스케줄 (TAS / GCL)

포트별 게이트 파라미터와 **게이트 컨트롤 리스트**를 읽어 인스펙터에 **타임라인**으로 그린다.
트래픽 클래스별로 한 줄, 창 너비는 지속시간에 비례한다. RECON 이 링크 고장 시 교체하는 것이
바로 이 스케줄이고, 숫자 표로는 그 교체가 보이지 않는다.

실기 검증 (LAN9692 포트 1): CLI 로 1 ms 주기 / TC7 500 µs → 전체 개방 500 µs 스케줄을 쓰고,
콘솔이 `Enabled, 1000.0 us cycle` 과 두 창 타임라인을 그대로 표시.

**태블릿에서 스케줄을 바꾸는 것까지 실기 검증됨.** 콘솔은 프리셋 이름만 보내고
(`!SCHED:<port>:<preset>`), 실제 엔트리는 컨트롤러가 만든다 — SID 테이블을 가진 쪽이자
카탈로그를 확인한 쪽이 컨트롤러이므로, 쓰기를 조립할 자격도 거기에 있다.

```
!SCHED:12:strict  ->  schedule 12 -> strict: accepted (last code 2.04)
```
타임라인이 TC7 250 µs → TC6 250 µs → 전체 개방 500 µs 로 바뀌는 것을 화면에서 확인.

프리셋은 다섯 번의 iPATCH 로 나간다: 컨트롤 리스트 → cycle numerator → denominator →
gate-enabled → **config-change**. 마지막 것이 admin 목록을 실제로 채택시키는 방아쇠다.
CLI 가 그렇게 보내므로 그 순서를 따랐다.

**업링크 포트에는 스케줄을 걸 수 없다.** 비활성화와 같은 이유다 — 관리 트래픽이 쓰는 게이트를
닫는 스케줄은 컨트롤러가 의존하는 링크를 굶기고, 스스로 되돌릴 수 없다. 어떤 스케줄이
살아남을 수 있는지 판별하는 대신 **통째로 거부한다**; 그 판단은 이 데모가 할 필요가 없다.

가드를 굽기 **전에** 업링크에 걸려 있던 시험용 스케줄을 시리얼로 먼저 지웠다. 순서를 바꿨으면
태블릿에서 지울 수 없는 스케줄이 남았을 것이다 — 가드는 `off` 도 함께 막기 때문이다.

쓰기용 YAML 형태 (`keti-tsn patch`):

```yaml
- ? ".../gate-parameter-table/admin-control-list/gate-control-entry"
  : - index: 0
      operation-name: ieee802-dot1q-sched:set-gate-states
      time-interval-value: 500000     # ns
      gate-states-value: 128          # TC7
- ? ".../admin-cycle-time/numerator"   { : 1 }
- ? ".../admin-cycle-time/denominator" { : 1000 }
- ? ".../gate-enabled"                 { : true }
- ? ".../config-change"                { : true }
```

게이트 엔트리는 **경계를 알리는 것이 없어 `index` 리프가 항목을 가른다** — 장비가 각 항목에서
그것을 먼저 보낸다.

## 시퀀스 = RECON 모드

시퀀스 하나가 **릴레이와 게이트 스케줄을 함께** 바꾼다. 과제의 요점이 "링크가 죽으면 스케줄이
바뀐다" 이므로, 릴레이만 넘기는 시나리오는 이야기의 절반만 보여준다.

| 시퀀스 | 패스 | 스위치 포트 1 스케줄 |
|--------|------|----------------------|
| Mode 0 - normal | 둘 다 정상 | `tc7` (1 ms) |
| Mode 1 - path 1 down | 1번 절단 | `strict` (1 ms, 3구간) |
| Mode 2 - path 2 down | 2번 절단 | `fast` (200 µs) |
| Mode 3 - both down | 둘 다 절단 | `off` |

실기 확인: `Mode 1` 탭 한 번에 `schedule 1 -> strict: accepted (2.04)` 와 Path 1 `Fault`.

스위치가 3대가 되면 모드별로 스위치마다 다른 스케줄을 지정하면 된다 — 시나리오 표에
포트 하나가 아니라 (스위치, 포트, 프리셋) 목록을 두는 형태로 넓히면 구조는 그대로다.

## 포트 물리 상태

링크 속도와 **버려진 프레임**(FCS / oversize / undersize)을 인스펙터에 표시한다. 링크가
up 이냐 down 이냐만 보여주는 콘솔은 **"올라와 있는데 상태가 나쁜 링크"**를 못 보여주는데,
그쪽이 더 흥미로운 고장이다. 둘 다 인터페이스 서브트리에 이미 실려 오므로 추가 요청은 없다.

`speed` 는 decimal64 라 CBOR **Tag(4) `[exponent, mantissa]`** 로 온다. 태그를 통째로
건너뛰면 조용히 사라지므로 따로 푼다 (`0.1` Gbps → 100 Mbps).

**알림 수를 줄여야 했다.** 포트 13개에 TAS/GCL/ETH 를 다 붙이니 스냅샷 하나가 40줄에
가까워졌고, 각 줄이 6 ms 간격이라 **버스트 꼬리가 유실됐다** — 속도 줄이 아예 도착하지 않았다.
지금은 **말할 것이 있는 포트만** 보낸다: 링크가 살아있거나, 오류 프레임이 있거나, 스케줄이
걸려 있는 포트.

## 조사했지만 안 붙인 것 (그리고 왜인지)

**LLDP 는 이 펌웨어 빌드에서 동작하지 않는다.** YANG 모델은 완전히 들어 있고
(`/lldp/port/admin-status` 11014, `/lldp/port/remote-systems-data` 11033 — 이웃 테이블이
있으므로 3대가 물리면 링 토폴로지를 그릴 수 있다) 쓰기도 **오류 없이 받아들여지지만**,
되읽으면 `port: []` 이고 `local-system-data: null` 이다. 리프만 patch 하면
`missing-element`(38444) 로 거부되고, 항목째로 만들면 수락되지만 아무것도 생기지 않는다.

**PTP 도 같은 모양이다**: `instances/instance: []`, `ltcs/ltc: []`. 인스턴스를 만들어 보는
것이 다음 단계이고 아직 안 해봤다.

**SID 는 미리 구워 뒀고, 파싱은 안 썼다.** 둘은 성격이 다르다 — SID 는 카탈로그에서 나오는
**사실**이라 미리 넣어도 틀릴 수 없고 나중에 한 단계를 없앤다. 반면 와이어 형식(CBOR 인코딩,
리스트 경계, 태그)에 대한 짐작은 이 프로젝트에서 네 번 틀렸다(iPATCH 형태, 키 조회, LED 핀,
decimal64). 그 부분은 장비가 실제로 보내는 바이트를 본 뒤에 쓰는 편이 결국 빠르다.

구워둔 SID: PTP `default-ds/clock-identity`(15159), `instance-enable`(15169),
`current-ds/offset-from-master`(15155), `parent-ds/…/clock-identity`(15218);
LLDP `port/admin-status`(11014), `remote-systems-data/chassis-id`(11034),
`port-id`(11042), `system-name`(11058).

그 밖에 카탈로그에 있는 것: PSFP(802.1Qci), frame preemption(802.1Qbu),
802.1CB **stream identification** (FRER 본체는 없음), ACL, aggregation, DHCP, hardware.

## 저장과 게이팅 해제

스케줄과 포트 상태는 **running config 에만** 있다. 재부팅하면 마지막으로 저장한 상태로
돌아간다. 콘솔의 두 동작:

| 동작 | 하는 일 | 안 하는 일 |
|------|---------|-----------|
| **Save to flash** | running config 를 flash 에 쓴다 (`save-config`, SID 21007, POST `{21007: null}`) | — |
| **Clear gating** | 스케줄이 걸린 포트의 gate-enabled 를 끄고 config-change 로 반영 | 업링크는 건드리지 않음. flash 를 쓰지 않음. 재부팅·IP·그 밖의 설정 일절 안 건드림 |

**"초기화"라고 부르지 않는다.** 이 장비에는 **공장 초기화 RPC 가 없다** — 카탈로그 전체를
뒤져도 없다. 있는 것은 `system-restart`(19018) 와 `system-shutdown`(19019) 뿐이고, 재부팅은
"저장된 상태로 되돌리기"이지 초기화가 아니다. 버튼은 **하는 일 그대로** 이름 붙였다:
"Reset" 은 스케줄 하나 지우는 것부터 장비를 밀어버리는 것까지 다 뜻할 수 있다.

**저장이 유용한 자리:**
- 관리 IP — 이미 저장했다. 없으면 재부팅 후 컨트롤러가 스위치에 닿지 못한다.
- **전원을 켜면 곧바로 있어야 할 기준 스케줄** — 데모장에서 정전이 나도 스위치가 알려진 TSN
  상태로 올라온다.
- 반대로 **고장 상태는 저장하지 말 것.** 주입해둔 고장이 flash 에 남으면 다음에 켤 때
  원인 모를 상태에서 시작한다. 지우고 나서 저장하는 순서가 맞다.

## FRER 은 이 장비에 없다

카탈로그에 `ieee802-dot1cb-stream-identification` (+`-dev`, `-types`) 은 있지만 이것은
스트림 **식별**(802.1CB 6장)이다. **복제/제거 본체(`ieee802-dot1cb-frer`)는 없고**,
sequence-generation / recovery 계열 노드도 카탈로그 전체에 하나도 없다. 매뉴얼과 일치한다.

## 보드 굽기 (tools/flash.sh)

```
tools/flash.sh switch          # 후보 포트와 MAC 을 보여준다
tools/flash.sh switch /dev/ttyACM3
tools/flash.sh path   /dev/ttyACM1
```

역할마다 보드 옵션이 다르다 — 컨트롤러는 16MB + 옥탈 PSRAM, 슈퍼미니는 4MB + 쿼드. 이걸
바꿔 구우면 **실패하지 않고 이상하게 동작하는** 보드가 나오므로, README 에 적어두고 복사하게
하는 대신 스크립트로 만들었다. 포트를 안 주면 ESP32-S3 로 보이는 포트를 **MAC 과 함께**
나열한다 — 새 보드를 컨트롤러 표에 넣을 때 필요한 값이 바로 그것이다.

### 보드 추가 절차 (전부 합쳐 세 단계)

1. `tools/flash.sh switch` 로 MAC 확인
2. `switch_controller.ino` 의 `kControllers` 에 한 줄 추가
   (MAC, 스위치번호, 자기 IP 끝자리, 스위치 IP 끝자리, 업링크 포트)
3. `tools/flash.sh switch <포트>` — 굽고 꽂으면 `KETI-SWITCH<n>` 으로 광고하고 콘솔이 잡는다

스위치 쪽에 관리 IP 가 없으면 그것만 시리얼로 한 번 만들어 준다
(`keti-tsn patch setup/setup-ip-static.yaml` → `post setup/save-config.yaml`).
**새 스위치는 카탈로그가 다를 수 있으므로 SID 테이블을 다시 뽑아야 한다** —
안 하면 컨트롤러가 `CATALOG_BAD` 로 거부하고 포트를 안 보낸다.

## 소크 (tools/soak.py)

`python3 tools/soak.py <분>` — 태블릿에서 RECON 모드를 20초마다 순환시키면서 컨트롤러
스냅샷이 계속 전진하는지 본다. **버튼이 한 번씩 되는 것은 리그를 두고 나가도 되는지에 대해
아무것도 증명하지 않는다** — 이전 데모는 단발 동작이 아니라 지속 운전에서 멈췄다.

2026-08-07 결과: **12분, 모드 전환 35회(8주기), 스냅샷 197개, 정지 0, 이상 0 — PASS.**

## 미확인 / 열린 항목

- **태블릿이 스위치 상태를 받는 경로.** ESP 를 경유할지, 태블릿이 직접 CoAP 를 말할지
  아직 정하지 않았다. 태블릿을 `192.168.1.30` 으로 같은 망에 넣으면 직결이 가능하다.
- **9662 두 데이터 포트의 물리적 결선.** 포트 1 이 up 이고 ESP 의 링크도 up 이므로 그 둘이
  이어져 있을 가능성이 높지만, 확인하지 않았다.
- **스위치가 물리적으로 하나뿐이다.** RECON 은 3× LAN9692 링이다. 코드는 3대까지 준비돼
  있지만(아래 참조) 실제로 여러 대와 붙여본 적은 없다.
- **업링크 포트 스케줄 가드가 없다.** 비활성화는 막았지만 TAS 스케줄은 막지 않았다.
- **SID 테이블 생성기.** `keti-tsn-cli` 의 캐시에서 필요한 경로만 뽑아 체크섬과 함께 굽는
  도구가 아직 없다.

## 하드웨어를 다룰 때 주의

**ESP32-S3의 GPIO19/20은 네이티브 USB D-/D+ 다.** 이 핀을 다른 용도로 재설정하면 USB가
즉시 끊기고, 보드는 BOOT 버튼을 누른 채 다시 꽂아야 복구된다. 핀을 훑는 프로브에서는
19/20을 반드시 제외할 것 — 한 번 당했다.
